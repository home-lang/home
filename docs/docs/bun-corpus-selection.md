# Native corpus selection

The native selection modules port the file-selection contracts in `scripts/runner.node.mjs` at Bun `4982b91e3702094330f3be3883354c52b8c01323`. Selection records describe coverage; they do not represent passing tests. Full CI setup and execution remain tracked in [#724](https://github.com/home-lang/home/issues/724), under [#66](https://github.com/home-lang/home/issues/66).

`corpus_selection.zig` parses expectation filenames, modifiers, values, comments, and original line numbers. The pinned runner excludes matching entries regardless of whether their value is `FAIL`, `FLAKY`, `SKIP`, or another label. Modifiers match with OR semantics and case-sensitive equality. Filename rules use normalized-path substring matching, including the upstream removal of the first `test/` occurrence. They are not globs.

Selection applies the macOS x64 CI Node-file classification rule, optional Node-only filtering, comma-separated includes/excludes, applicable expectations, positional filters, and sharding in upstream order. Positional filters take precedence over sharding. Modified tests receive stable priority after selection. The acceptance API does not offer random smoke sampling.

Call `corpus_runner.runGateWithOptions` with a `SelectionPolicy` to apply these rules to native execution. The policy carries platform/build context, original expectation source bytes, optional Home expectation source bytes, and filter/shard options. Set `detect_platform: true` to replace the platform fields with native host probes, and supply `expected_platform` to enforce the pinned expected-agent checks before discovery or execution. The effective context and expectations are journaled. A Home-only exclusion fails before any child starts. Removing an upstream exclusion is permitted and recorded as additional Home coverage. Explicit file, directory, and named-subset runs preserve their requested paths.

When persistence is enabled, a `selection` journal event records the complete discovery inventory, ordered selected indices, excluded indices and reasons, expectation metadata and source hashes, effective modifiers, additional Home coverage, and the execution range. The selected/excluded sets must partition the inventory. Start/limit applies after selection; files outside that range remain visible in the policy record. The outcome validator rejects an execution selection that disagrees with this record. Exclusions do not increase registered skip or pass counts.

`corpus_vendor.zig` implements vendor filename selection and recursive discovery. It uses Home's native ECMAScript regular-expression engine for upstream `skipTests` patterns: `*` becomes `.*`, while other regex syntax remains active. Explicit `testExtensions` bypass ordinary test classification and `skipTests`, as in the pinned runner. Recursive entry order, filename filters, skip reasons, and project defaults remain distinct from installation and execution outcomes.

For differential selection audits, compile `packages/home_test/src/corpus_selection_probe.zig` as a native executable and pass input/output JSON paths. Its `Input` type defines the file inventory, original/Home expectation text, and context/options pairs. Output files are created exclusively and labeled `selection-only`. This diagnostic does not execute JavaScript or award corpus pass credit.

The default corpus CLI has not yet been connected to complete CI orchestration. Callers of the selection API may supply platform context or request native host detection and expected-agent checks. Native root/test installation, explicit remap service lifetime, and explicit vendor preparation are available as separate operations. Their original ordering and selection gates in a unified CI coordinator remain unfinished. The Elysia checkout under `packages/runtime/test/vendor/` is generated data and is ignored by Git. Its pinned source revision and setup evidence must be retained when evaluating the complete suite.

## Native platform checks and launch context

`home test --bun-corpus-platform` reports the actual host and checks the `EXPECTED_PLATFORM_OS`, `ARCH`, `ABI`, `DISTRO` and `RELEASE` variables (each with the `EXPECTED_PLATFORM_` prefix). It reports mismatches and exits unsuccessfully when a declared value does not match. As in pinned CI, an absent or empty expected OS disables the expectation check. Release comparisons accept complete dotted prefixes: `27` matches `27.0`, while `270` does not. Failed probes stay undetected and cannot satisfy a declared expectation.

`corpus_platform.zig` uses native process architecture and OS, the original release/loader-file precedence, and the original `sw_vers`, `ldd`, `lsb_release`, or `cmd /c ver` probes. Alpine release suffixes, quoted os-release fields, successful command status and unknown results retain their distinct meanings. The CLI's CI flag uses the original exact `true` checks for `CI`, `BUILDKITE` and `GITHUB_ACTIONS`; `CI=1` alone does not set it.

For `runGateWithOptions`, `SelectionPolicy.detect_platform` derives the platform fields used by selection. `expected_platform` validates the host before discovery; `context.is_ci` remains the caller's chosen CI/local execution mode and `asan_step` carries the upstream build-step classification. Those two launch settings now reach every selected child instead of execution silently using the default CI profile. Local Node files therefore receive the original 60-second deadline and local validation settings. The outcome validator checks declared native platform expectations and the types of the recorded launch settings.

This does not complete the default CI coordinator or bypass the failing original primary installation in #725. The native platform command reports host state without executing corpus files. `corpus_platform_probe.zig` supports comparisons of recorded observations and expected-agent checks; simulated Linux/Windows observations do not establish native execution on those platforms.
